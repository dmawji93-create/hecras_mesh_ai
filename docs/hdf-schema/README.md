# HEC-RAS geometry HDF schema notes

Reverse-engineered notes from inspecting Muncie's `Muncie.g04.hdf` and Bald
Eagle's `BaldEagleDamBrk.g09.hdf` on 2026-05-24. Generated by
`hecras_mesh_ai.harness.inspect.dump_structure`. **USACE has not published the
schema** — these notes are our best understanding, derived empirically.

Raw structure dumps:
- [muncie-g04.md](muncie-g04.md) — HEC-RAS 6.3 Beta 2, 5,391 cells, 2 breaklines, no embedded CRS
- [bald-eagle-g09.md](bald-eagle-g09.md) — HEC-RAS 6.2.0, 18,066 cells, 4 breaklines, embedded CRS EPSG:2271

## Top-level structure

```
/                                            File Type, File Version, Units System, [Projection]
└── Geometry                                 Extents, Geometry Time, Title
    ├── 2D Flow Area Break Lines             ← the writeable target for our project
    ├── 2D Flow Areas
    │   ├── <area name> (e.g. "BaldEagleCr") cell + face topology, sub-grid bathymetry
    │   ├── Attributes                       per-area: Name, Mann, cell tolerances, Spacing dx/dy, ...
    │   ├── Cell Info, Cell Points           computation-point info
    │   └── Polygon Info, Parts, Points      the 2D-area perimeter polygon
    ├── Cross Sections                       1D cross sections (61 in Muncie, 0 in Bald Eagle)
    ├── Land Cover (Manning's n)             roughness polygons
    ├── River Centerlines                    1D river network
    └── Structures                           bridges, weirs, lateral structures
```

## The unifying "polyline" subschema

Every linear feature (breaklines, river centerlines, structure centerlines,
cross-section polylines) uses the **same five-dataset pattern**:

```
<feature group>/
├── Attributes        compound dtype, one record per feature (Name + per-feature params)
├── Polyline Info     (N_features, 4) int32: Point Starting Index, Point Count, Part Starting Index, Part Count
├── Polyline Parts    (N_parts, 2)    int32: Point Starting Index, Point Count
└── Polyline Points   (N_total_points, 2) float64: X, Y
```

For single-part polylines, `Polyline Parts` has one row per feature with the
same indices as `Polyline Info`.

**Breaklines `Attributes` compound dtype** (verified in both pilots):
```python
[('Name',              'S32'),  # breakline name (e.g. "SayersDam", "Road 1")
 ('Cell Spacing Near', '<f4'),  # ft; HEC-RAS mesh-generation parameter
 ('Cell Spacing Far',  '<f4'),  # ft
 ('Near Repeats',      '<i4'),  # how many cell rows of "near" spacing along the line
 ('Protection Radius', 'u1')]   # uint8 flag
```

## What's input vs derived

Many `/Geometry/2D Flow Areas/<area>/Cells*` and `Faces*` datasets are
**derived** by HEC-RAS during "Generate Computation Points" / mesh
regeneration. The schema includes both the **inputs** (computation points,
perimeter polygon, breaklines, refinement regions) and the **derived mesh**
(cell centers, face topology, sub-grid bathymetry tables).

Inputs we'd need to write to drive a full mesh regeneration:
- `/Geometry/2D Flow Areas/Polygon Points` — the 2D-area perimeter
- `/Geometry/2D Flow Areas/Cell Points` — computation points (cell centers before perturbation)
- `/Geometry/2D Flow Area Break Lines/*` — breaklines
- `/Geometry/2D Flow Area Refinement Regions/*` — refinement regions (absent in both pilots)
- Plus `/Geometry/2D Flow Areas/Attributes` row with the area name and spacing defaults

Derived data HEC-RAS will recompute on "Generate Mesh":
- `Cells Center Coordinate`, `Cells FacePoint Indexes`, all `Faces *` topology
- `Cells Volume Elevation Values`, `Faces Area Elevation Values` (sub-grid bathymetry tables — computed from the terrain TIFF)

## Strategic implication for our writer (Stage 4 Task 2)

**Two writer modes, increasing in scope:**

### Mode A — "Breakline replacement" (the realistic Stage 4 Task 2 target)

Take an existing valid geometry HDF, replace just `/Geometry/2D Flow Area
Break Lines/*`, save as a new geometry HDF. HEC-RAS will pick up the new
breaklines on its next "Generate Mesh" trigger.

Implementation surface: tiny — 4 datasets to write, all simple shapes. Round
trip is straightforward.

This is the writer we actually need for the ML pipeline: model predicts
breaklines → replace → re-mesh in HEC-RAS → run.

### Mode B — "Full geometry from scratch" (deferred)

Build a complete valid geometry from terrain + computation points + perimeter
+ breaklines, with HEC-RAS doing the Voronoi triangulation on first open.
Bigger surface, more risk. Deferred unless the ML workflow ever needs to
emit standalone geometries (it doesn't for v1).

## Open questions

- **HEC-RAS version compatibility.** Muncie was saved with HEC-RAS 6.3 Beta 2
  (Dec 2019); Bald Eagle with 6.2.0 (Mar 2022). Bald Eagle has additional
  derived datasets (`Cells Center Manning's n`, sub-grid bathymetry tables,
  `Infiltration/*`) not present in Muncie. **Question:** does HEC-RAS 7.0
  (current at 2026) require the newer derived datasets to be present when
  reading an older-format HDF? Answer: test by writing Muncie-style and
  opening in current HEC-RAS.
- **The "Generate Mesh" trigger from outside HEC-RAS.** RAS Mapper does it
  on a UI button. The HECRASController COM interface should expose this
  programmatically. Verify in Stage 4 Task 3.
- **Refinement Region writer.** Neither pilot has refinement regions, so the
  refinement-region subschema is empirically unknown to us. Need a FEMA bulk
  corpus example that does (Phase 3A NOAA OWP corpus is likely source).
